## 한 줄 요약

gajae-code가 mdr에 주는 것은 새 기능이 아니라 **강제 계층(enforcement layer)** 이다. mdr 기준선 실측 결과, 약점 10곳이 전부 "프롬프트 지시는 있는데 스크립트 강제가 없는 곳"에 몰려 있는데, GJC는 정확히 그 지점을 다루는 시스템이다 — 철학은 세 문장으로 요약된다:

1. **모델의 자기신고를 믿지 않는다.** 완료·검증·리뷰의 모든 판정을 내구 파일 영수증(ledger.jsonl)과 자동 계산 해시에 결박하고, 모델이 손으로 채운 값이 실제와 다르면 fail-closed로 거부한다 (ultragoal/SKILL.md:14, :233).
2. **상태를 디스크에 외부화한다.** 게이트 진행·검증 이력이 세션 컨텍스트에만 살면 압축 한 번에 증발한다 — append-only 원장 + 포인터로 어느 시점에 죽어도 결정론적으로 재개한다 (docs/session.md:62-68, docs/compaction.md:142).
3. **루프에는 런타임 상한을, 종결에는 독립 판정을 건다.** 반복 상한 초과는 exit 3 + STUCK 마커로 종결하고(fail-open 방지: 장부와 디스크 파일 수의 max로 판정), 완료·포기는 독립 크리틱의 기계파싱 가능 verdict 없이는 성립하지 않는다 (ralplan/SKILL.md:94,126; ultragoal/SKILL.md:392,422).

같은 원리를 이 메모 자체에도 적용했다: 초안의 R항목 중 **자가신고를 필드 수만 늘려 재생산하던 것(R2a 초안), 실측 결함의 발생 경로를 비껴가던 것(R5 초안), 이미 구현돼 있던 것(원자쓰기), 실측 근거 없는 사변(G0 인터뷰 3종)** 을 크리틱 라운드가 잡아냈고, 아래는 그 수정본이다.

## P0 — 강제 계층 (실측 약점 직결, 최고 레버리지)

### R1. 게이트 영수증 원장 (`audit/gates.jsonl`) ★최고 레버리지

- **왜**: mdr의 최대 구조 리스크는 "게이트 진행 상태가 팀리드 컨텍스트에만 산다"는 것이다(약점 #1, #9). 수 시간 조사 중 압축이 일어나면 '지금 어느 게이트인가, 어떤 게이트를 통과했는가'가 증발하고, [4b] 재봉인처럼 건너뛰어도 아무도 못 잡는 수동 절차는 가장 새기 쉬운 실패다. GJC의 답: **"완료는 내구 파일 + 신선한 영수증으로만 검증하며, 상태 필드 값 자체는 증거가 아니다"**(ultragoal/SKILL.md:14, :322).
- **설계 (크리틱 반영: 영수증 기록 주체를 이원화)**:
  - **스크립트 판정 게이트(G3·G5c·[4b]·G5)는 스크립트가 자기 결과를 직접 영수증으로 기록한다** — verify_facts.py·manifest.py가 PASS 시 {gate, ts, exit, 결과 요약 해시, facts_db_sha}를 gates.jsonl에 append. 리드가 "verify_facts 통과"라고 수동 기록하는 경로 자체가 없다("mechanical한 것은 전부 자동 채움" — ultragoal:233의 전면 적용. 초안은 이를 [4b]에만 적용하는 오류가 있었다).
  - **육안·판단형 게이트(G0 승인·[2] 완료 선언·G4 preview)만 `gates.py record`(리드 수동)** — 단 빈 evidence 거부 + `refs` 산출물 경로 실재·해시 검사. 수동 영수증은 "일을 했다"의 증명이 아니라 "기록을 남겼다"의 증명임을 문서에 정직하게 명시한다(과장 금지 — 실질 방어는 refs 결박과 후속 스크립트 게이트가 담당).
  - **전제조건 훅**: verify_facts는 G1·[2] 영수증을, render_pdf는 G3 PASS 영수증을, manifest verify는 [4b] 영수증을 요구(없으면 exit≠0 + 이유 출력). **[4b] 자동화**: render_pdf가 렌더 성공 직후 manifest build를 스스로 호출하고 영수증 기록 — "건너뛰면 잡힌다"에서 "건너뛸 수 없다"로.
  - **상태 조회는 파생으로**: ~~STATE.json~~ 별도 상태 파일은 두지 않는다(진실원천 이원화 + 대조 유지비 — 크리틱 지적 수용). `gates.py status`가 원장 꼬리를 읽어 {현재 게이트, 완료 목록, facts_db 경로}를 출력 — 재개 프로토콜과 압축 대비 상태 확인이 이 한 명령으로 해결된다.
- **얼마나**: 中. 신규 스크립트 1개(~100줄) + 기존 스크립트 3곳에 자기기록·전제조건 + SKILL.md 게이트 절차 갱신.
- **위험**: 수동 영수증 게이트(G0/[2]/G4)는 여전히 자기신고다 — 이 계층의 실질 방어는 R2a(재열람 기계 결박)와 R6a(독립 크리틱)가 맡고, R1은 "기록 없이 넘어가는" 실패만 잡는다는 한계를 명시해 둔다.

### R2. 검증 영수증 강화 3종 — 재열람 기계 결박 · 신선도 검증 · risk 자동판정

- **왜**: [2] 전건 재검증은 mdr의 심장인데 실측 구멍이 셋이다(약점 #2·2′·3·4). 초안의 "verify_event에 필드 추가" 접근은 크리틱이 정확히 반박했다 — **리드가 채우는 필드는 몇 개를 늘려도 자가신고다**(기존 evidence.verbatim을 복사하면 재열람 없이 전 필드 충족). 수정본은 기록 주체를 모델에서 기계로 옮긴다.
- **이식 (크리틱 반영판)**:
  - **(R2a) fetch-log 기계 결박**: 재열람을 fetch.py 경유로 강제하고, **fetch.py가 자체 로그**(`audit/fetch-log.jsonl`: url·ts·HTTP 결과·본문 sha·스냅샷 파일 경로)를 **기계 기록**한다. verify_event는 fetch-log 항목 참조(`fetch_ref`)가 필수이고, verify_facts가 (a) fetch_ref 실재, (b) `matched_verbatim ∈ 스냅샷 본문`을 기계 대조한다. 리드가 재열람을 안 했으면 참조할 로그 항목 자체가 없다 — 약점 #2가 필드가 아니라 **증거 사슬**로 닫힌다. WebFetch로 열람한 경우는 스냅샷이 없으므로, 핵심수치(high-risk)는 fetch.py 재열람을 요구하고 그 외는 WebFetch+수동 verbatim을 허용하는 2단으로 시작(전건 fetch.py 강제는 비용 실측 후 결정).
  - **(R2b) 신선도는 검증 시점 계산으로**: 초안의 "수정 시 stale 마킹"은 개입 지점이 없다(facts_db에 수정 API가 없고 직접 재작성이 유일 경로 — 크리틱 실측). 수정본: **verify_facts가 현재 fact 내용 해시와 verify_event.content_sha를 대조해 불일치면 stale FAIL** — 어떤 경로로 수정됐든 검증 시점에 잡힌다(쓰기 훅 불요, R2a의 content_sha가 그대로 재료). 주장 내용 무변경 수정(표현만)은 리드 자기인증 면제 등급.
  - **(R2c) risk 자동판정 2단 + [Bx] FAIL 승격**: "적용 가능성은 런타임이 결정, fail-closed"(ultragoal:311). 현 `_HIGH_RISK_METRICS`는 영문 substring이라 한글 표기("시장규모"·"시장 크기")가 빠져나간다(크리틱 실측) — **한글·동의어 렉시콘 추가** + **2단 규칙**: metric 렉시콘 매칭 시 자동 high 취급·4요건 FAIL 승격, 통화/% 단위 단독은 warning 유지(전 매출·가격 수치의 FAIL 폭탄 방지 — 과소보다 과잉이 더 위험하다는 트레이드오프를 명시적으로 채택). `enhancement-directions.md` §B의 "다음 배치 승격 예고"를 이 형태로 이행.
- **얼마나**: 中上. fetch.py 로그 계층 + facts_db 스키마 + verify_facts 검사 3종.
- **위험**: fetch-log 결박은 fetch.py가 못 여는 소스(브라우저 전용 SPA 등)에서 마찰 — 그 경우 agent-browser 캡처(G2)를 fetch_ref 대체 증거로 인정하는 예외 경로를 두되 verify_event에 예외 사유 명기(무단 대체 금지 원칙, eval.md:118).

### R3. 상충 disposition 게이트 — "조사마다 수치가 달라지는 문제"의 정면 처방

- **왜**: 워커 A와 B가 같은 지표에 다른 수치를 반환할 때, 지금은 리드가 암묵적으로 한쪽을 고른다(약점 #5). 크리틱이 더 나쁜 사실을 실측했다: **현 구조가 이 실패를 유도한다** — add_fact가 동일 claim_key를 예외로 거부하고(facts_db.py:208-210) 무결성 검사도 중복을 failure로 처리하므로(verify_facts.py:352-353), 상충 수치는 대장에 공존조차 못 하고 두 번째 값을 조용히 버리는 것이 최소저항 경로다. 다음 조사에서 리드가 반대쪽을 버리면 수치가 달라진다 — mdr의 존재 이유가 걸린 구멍.
- **설계 (크리틱 반영: 불변식 개정급임을 인정)**:
  - add_fact의 동일 claim_key 거부를 **"shadowed 변이행 등재 + conflict 레코드 자동 생성"** 으로 개정(무결성 검사도 shadowed 허용으로 함께 개정 — first-wins+_shadowed 패턴, rulebook-matching:139). 상충 수치가 대장에 남아야 처분도 독립수렴 카운트("같은 수치를 몇 개 독립 출처가 보고했나")도 가능해진다.
  - conflict 레코드에 **명시적 처분 필수**(typed conflict gate, ralplan:74): accept_a | accept_b | synthesize | defer_user | both_shown(disputed 병기) + rationale + 결정 주체. **disposition 미기록 conflict 존재 시 G3 본문 결박 거부**(fail-closed). 처분 근거 어휘는 기존 규칙 정식화: 기본소스 우선 / 최신 valid_at 우선 / 정의차 병기.
  - 완전일치 감지만으로는 워커 B가 period를 "FY2024"로만 써도 빠져나간다(크리틱 지적) — **metric+entity 동일 & period/geo 정규화 기반 conflict 후보**를 disposition 필수는 아니되 경고로 표면화하는 2단 감지.
- **얼마나**: **中上~上**(초안 '中'은 과소평가 — add_fact 유일성 불변식·ledger-integrity·diff 로직까지 손대는 불변식 개정급). 유지비: claim_key 정규화 규칙이 살아있는 유지 대상이 된다.
- **위험**: '같은 지표' 오탐이 리드를 소모 — 후보 경고는 처분 강제 없이 시작하고, 정규화 렉시콘은 실전 조사에서 축적.

### R4. 마커 파서 + 재발주 예산 — [E] 루프의 스크립트화

- **왜**: 워커 마커의 "기계 파싱"이 실제로는 리드 수동이고(약점 #6), [E] 루프의 수렴 판정·깊이캡이 전량 리드 감각이다(약점 #7).

  - `expansion-log.md`를 파싱 가능 형식으로 개정 + parse_markers가 웨이브 수·축별 잔여 리드를 집계 출력 → 수렴 판정이 감각이 아니라 카운터가 된다. 깊이캡 도달 시 **RESEARCH-STUCK 명시 종결**(ralplan:93-94 번역): 미수렴 축은 '미확정(상충 병기)'로 강등 등재하되 확정 수치 승격 금지.

### R5. 캡처 검증 — 소비자측 전수 검사 (경로 독립)

- **왜**: 백지 PNG 실측 결함(약점 #8)의 발생 경로는 **agent-browser MCP가 직접 저장하는 스크린샷**인데, 초안은 검사를 capture_*.py(그 경로를 지나지 않는 스크립트)에 두는 위치 오류였다 — 두 크리틱이 동일 지적. 생산자가 여럿이면 검사는 소비자 쪽 한 곳에 둔다.
- **설계 (재설계판)**:
  - **(R5a) `check_captures.py` 또는 verify_facts 캡처 루프(432-449행) 확장**: `_captures/**` 전수를 **생산 경로 무관하게** 픽셀 분산·유효 엔트로피 하한 검사(단색·준백지 → FAIL). G2/G3 판정 + R1 영수증에 결박. 육안(G4)을 대체하는 게 아니라 앞당기는 것 — 스크립트가 백지를 거르고 육안은 오귀속(엉뚱한 페이지)만 본다.
  - **(R5b) provenance 메타**: 자동 기록이 가능한 생산자(capture_pdf 등)는 스크립트가 기록하고, **agent-browser 캡처는 리드가 캡처 직후 메타 JSON({최종 URL, 시각, 사다리 계층, 라이브/아카이브})을 남기는 절차**로 현실화(MCP 저장물엔 통과 스크립트가 없다는 실측 반영). check_captures가 메타 JSON 실재를 검사. 장기적으로 캡처를 얇은 래퍼 스크립트 경유로 일원화하는 옵션은 Group G(브라우저 엔진) 배치에서 재평가.
  - **(R5c) fresh 규칙**: R2b와 연동 — fact 수정 후 옛 캡처 재사용은 content_sha 불일치로 검증 시점에 잡힌다.
- **얼마나**: 小~中. 검사 스크립트 1개 중심.
- **위험**: 분산 하한이 높으면 여백 많은 문서 페이지 오탐 — 임계값은 실측 백지 샘플로 캘리브레이션.

### N9. 계획 red-team 패널 (측면 패널의 조건부 발동판)

- **트위스트 핵심**: 3기 상시를 **1기 3렌즈 + 조건부 발동**으로 압축(deep-interview:627의 독립 컨텍스트 요건은 유지).
- **발동 조건**: 대형 조사(축 5+ / 실사·BM 유형 / 사용자 명시 요청)의 G0 승인 직전 1회. **렌즈별 독립 스폰 3기(sonnet 소형·병렬)** — contrarian("이 비교축은 실제 결정에 쓰이나")·simplifier("절반 범위로 같은 결정 가능한가")·researcher("이 데이터는 애초에 공개돼 있나 — 조사 불가능 축 사전 탐지"). 초안의 "1기 3렌즈 통합"은 폐기(크리틱 반영: 한 컨텍스트 안에서 렌즈끼리 상호 앵커링되면 원 3기 설계가 막던 오염을 재생산 — deep-interview:627 "no persona anchors on another's framing". 비용 제약은 3렌즈 통합이 아니라 **조건부 발동 + sonnet 소형**이 이미 중화). 각 기는 **조사 대화 미공유(fresh context)**, 반환은 최고 레버리지 맹점 1건 구조화 마커 — **질문 추가·범위 변경·완료 선언 권한 없음**, 발견은 승인 질문의 선택지로만 접힌다(lateral-review-panel.md:20). 기존 `business-frameworks.md` red-team 렌즈와 결합해 "계획 red-team"으로 명명(스킬 기존 어휘와 정합).
- **얼마나**: 小~中(프롬프트 규약 중심). R6a 터미널 크리틱과 대칭: N9는 입구(계획), R6a는 출구(보고서).

### N군 공통 안전장치

원 비채택 사유가 경고했던 실패는 트위스트로도 완전히 사라지지 않는다 — 잔여 위험을 정직하게 남긴다: N1 슬롯 형식주의(내용 부실은 못 잡음), N4 정규화 매칭 한계(표기 변형) + EXPAND 리드 단계 엔티티 미포착 사각, N6 골든 갱신 태만, N9 발동 조건의 자의적 축소.

**존치 심사 (집계의 기계화 — 크리틱 반영)**: 구현 후 실전 조사에서 항목별 실적을 심사해, 실적 없는 자물쇠는 떼는 것도 하네싱이다(loop-until-dry의 역방향). 단 집계가 리드 자가신고면 1원칙과 자기모순이므로:
- **집계 재료는 기계 기록만**: 스크립트 게이트(N1·N3·N8)는 발동/차단 시 gates.jsonl에 자동 append. 규약 항목(N2·N7·N9)은 산출물 실재(가정 테이블·기각 기록·red-team 마커 파일)를 스크립트가 글롭 집계.
- **발동 기회 0 ≠ 검출 0**: 발동 조건 미충족 조사(소형이라 N5·N7·N9가 정상 휴면)는 그 항목의 심사 분모에서 제외. **"발동 조건을 충족한 조사 2건 연속 검출 0건"** 인 항목만 비채택 후보로 강등 심사.

## 구현 순서 제안

의존 관계상 R1이 기반이고, R2·R3가 증거모델 직결이라 선행 가치가 크다. N군은 대부분 R군 위에 얹히는 소형 항목이라 해당 R과 같은 배치에 묶는다.

1. **1차 (강제 계층)**: R1 게이트 원장(스크립트 자기기록 + 전제조건 + [4b] 자동화) → R2 검증 3종(fetch-log가 R2a·R2b의 공통 기반) → R3 상충 disposition(불변식 개정이라 단독 배치 권장 — add_fact·ledger-integrity·diff 회귀 확인 필수). **+N8**(G0 영수증에 계획 해시 1필드 — R1과 동시 구현이 가장 쌈), **+N1 G0 준비도**(서식 개정 포함). ※ enhancement-directions §B의 "[Bx] FAIL 승격 다음 배치" 약속이 R2c로 이행됨.
2. **2차 (수렴·품질)**: R4 마커 파서(**+N3 워커 장부·+N4 엔티티 카운터** — 파서 부속) → R5 캡처 소비자측 검사 → R6 종결 계층(**+N7 5조 규약** — R6a·R3 위의 규칙 문장) → **+N1 G3 플로어**(재료인 R2b·R3·R5 산출값이 이 시점에야 전부 존재 — 크리틱 반영으로 1차에서 이동).
3. **3차 (지속성·경제·입구)**: R7·R8a·R9 + injection flag + **N2 G0 확장·N9 계획 red-team·N5 계산 세션·N6 골든 세트**. 대부분 문서·규약 중심. R9c는 Group C 구현 배치와 합류.
4. 각 배치 후 plan-v2의 적대적 fixture·E2E 스모크 계획과 합류. **신규 게이트도 fixture 대상에 추가**: 빈 evidence 영수증 / fetch_ref 없는 verify_event / content_sha 불일치(stale) 결박 시도 / 미처분 conflict 통과 시도 / 백지 캡처 통과 시도 / 마커 구조 위반 / **빈 슬롯 팬아웃 시도(N1) / 장부 미terminal join 시도(N3) / 계획 해시 불일치 통과 시도(N8)**.
5. **N군 존치 심사**(N군 공통 안전장치 절): 1차 배치 후 실전 조사 2건에서 항목별 발동·검출 실적을 집계 — 2회 연속 0건 항목은 비채택 후보로 강등 심사.

**유지비 정직 병기**: R1·R2·R3·R4는 스크립트 강제라 스킬 개정 시 검사 로직도 함께 갱신해야 하는 이중 유지 부담이 생긴다(특히 R3는 claim_key 정규화 렉시콘이 살아있는 유지 대상). GJC의 이중 계층 가드 교훈(handoff-generation-pipeline:38)대로 **검사 로직은 스크립트 한 곳에 두고 여러 게이트가 같은 스크립트를 호출**하게 해 드리프트를 막는다.

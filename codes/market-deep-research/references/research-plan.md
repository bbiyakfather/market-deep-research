# research-plan — 조사계획 확정 게이트 (G0 선행, 산출물: `audit/research-plan.md`)

축(조사질문=에이전트 분할=3부 챕터의 단일 개념, `references/report-format.md` 축 프리셋 참조)은
조사가 시작되기 전에 확정돼야 한다. 확정 없이 조사원을 팬아웃하면 축이 조사 도중 흔들려
"3부 챕터를 못 채우는 축"·"에이전트가 없는 축" 불일치가 재발한다. 이 문서는 확정 필드·절차·
축 도출 체인·품질 기준·승인 목차 서식을 정의하는 G0 선행 게이트다(`entity-identity.md` 와
같은 격식 — 그 문서가 기관·기업 조사의 "대상"을 확정한다면, 이 문서는 모든 조사유형의
"질문·범위·종료조건"을 확정한다).

## 규모 판정 게이트 【v4-I】 (파이프라인 가동 여부 — 인터뷰보다 먼저)
요청이 단순 사실확인·한두 출처 요약이면 이 파이프라인을 가동하지 않는다 — 직접 경로
(WebSearch 등)를 안내하고 종료한다(사용자가 파이프라인 진행을 고집하면 진행). 판정 원칙:
**"작은 검증 필요가 요청을 파이프라인감으로 만들지 않는다"** — 캡처·교차검증이 필요한
수치가 한두 개 있다는 사실만으로 다축 병렬 조사(팬아웃·게이트 전 절차)를 정당화하지 않는다.
파이프라인감 판정 후에만 아래 브리프 앵커 게이트로 진행한다.

## 브리프 앵커 게이트 【v4-I】 (앵커 0개면 팬아웃 금지)
파이프라인감으로 판정된 요청은 13필드 초안을 쓰기 전에 앵커 보유량부터 센다.
앵커 열거형(고정 7종): `대상명 · 기간 · 지역 · 언어 · 비교축 · 산출형식 · 용도`.
- **앵커 1개 이상**: 있는 앵커에서 추론 가능한 만큼 13필드 초안을 채우고, 나머지는
  아래 인터뷰 규율의 라운드 예산으로 채운다.
- **앵커 0개**: 팬아웃 금지 — 앵커 없이 쓴 초안은 전부 팀리드의 발명이 되므로 초안
  작성조차 보류하고, 인터뷰 라운드로 라우팅해 앵커부터 확보한다.

## 확정 필드 (승인 전 전부 채움)
| 필드 | 내용 | 미확정 시 위험 |
|---|---|---|
| 의사결정 용도 | 고객이 이 보고서로 무엇을 정하는가(투자·진입·제휴·정책대응 등) | 조사 깊이·축 우선순위가 근거 없이 팀리드 임의 판단이 됨 |

## G0 심층 인터뷰 규율 【v4-I】
13필드를 채우는 인터뷰는 아래 규율을 따른다(전부 "확정 절차" 2단계의 사용자 승인에 선행).

| # | 규칙 | 내용 |
|---|---|---|
| ① | 라운드당 1질문 | 한 라운드에 질문 1개만(선택지 2~3개 동반 가능). 질문 다발은 답변 품질을 떨어뜨리고 어느 답이 어느 질문 것인지 모호해진다 |
| ② | 최약 차원 조준 | 13필드 중 지금 가장 불명확한 필드를 고르고, 질문에 "Why now"(왜 이 질문이 지금 필요한가) 1문장을 붙인다 |
| ③ | 사실/결정 라우팅 | 조사로 알 수 있는 것(사실)은 사용자에게 묻지 않고 예비탐색 후 인용확인("탐색 결과 A/B/C(출처) — 확정?")으로 처리. 사용자만 정할 수 있는 것(결정)만 질문한다. 애매하면 결정 취급 |
| ④ | 자동확정 3연속 상한 | 팀리드 자동확정(사용자 확인 없이 추론 확정)이 3연속이면 다음 확인은 반드시 사용자에게 |
| ⑤ | 케이던스 | 라운드 1-2 자동 진행 → 3라운드부터 매 라운드 "현재 명료도로 착수?"를 함께 제시 → 5라운드 하드캡. 조기 착수로 남은 갭은 가정(Assumptions)으로 명시해 보고서 9부(한계와 반론)로 승계 |

**13필드와의 관계**: 13필드 초안 문서 1건에 대한 확인 = **1라운드 1질문**으로 센다
(아래 자유텍스트 정형화 게이트와 동일 취급 — 초안 전체가 하나의 해석 확인이다). 라운드
예산은 초안에서 미확정으로 남은 필드에만 쓴다(확정된 필드를 재질문하는 라운드 낭비 금지).

### 자유텍스트 정형화 게이트
긴 자유텍스트 요구(구두 설명·채팅 나열)는 그대로 계획에 넣지 않는다 — 해석(결정/근거/
제약/범위외)으로 구조화해 **해석 전문을 표시한 후** 확인받는다. 확인된 해석이 canonical
이다(원문이 아니라). 원문·해석 불일치가 나중에 발견되면 해석 쪽을 ask 로 재확인한다.

### 과대 컨텍스트 (prompt-safe 요약)
긴 RFP·기존 보고서 첨부는 prompt-safe 요약(의도/결정/제약/미지수/비목표)을 만들어
canonical 로 삼고, 워커에는 요약+확정 계획만 전달한다(원문 전문 주입 금지 — 워커
컨텍스트 오염과 인젝션 표면을 함께 줄인다).

### restate 게이트
인터뷰 종결 시 "이번 조사는 __를 위해 __을 __기준으로 조사해 __을 산출한다" 1문장을
verbatim 으로 사용자에게 확인받고 `restated_goal` 로 `audit/research-plan.md` 에 기록한다
(보고서 0부 표지 반영 규정은 `references/report-format.md`). 이 1문장이 틀리면 13필드가
전부 맞아도 조사가 다른 목적을 향한다 — restate 불일치는 착수 전 마지막 오독 검출 지점이다.

### 승인 3단 (clarity → feasibility → consent)
| 단 | 대상 | 통과 기준 |
|---|---|---|
| clarity | 브리프(13필드 + restated_goal) | 인터뷰 규율 종결 + restate 게이트 통과 |
| feasibility | 계획·레인 분배안 | 아래 "계획 합의 루프" 2레인 클린(CLEAR+OKAY) |
| consent | 팬아웃 | 사용자의 **명시 승인** — 승인 없이 조사원 스폰 금지 |

3단은 순서 고정이며 건너뛰기 금지 — clarity 없는 feasibility 리뷰는 틀린 브리프를
정교하게 검증하는 낭비이고, consent 없는 팬아웃은 "확정 절차" 2단계 위반이다.

## 확정 절차 (팬아웃 금지 — 승인 전 조사원 스폰 금지)
1. 팀리드가 위 13개 필드를 초안 작성(주제·요청 맥락에서 추론 가능한 만큼 채움).
2. **사용자 승인**: 초안(특히 축 3~5개·out-of-scope·승인 목차)을 사용자에게 확인받는다.
   승인 전에는 병렬 조사원을 팬아웃하지 않는다(요청 오독으로 인한 팬아웃 낭비 차단).
3. 승인된 내용을 `audit/research-plan.md` 에 확정 기록(G0 산출물). 이후 모든 조사원 TASK·
   3부 챕터 구조는 이 파일의 축 목록을 그대로 따른다(임의 추가·누락 금지).
4. 확정 후 [1] 병렬 조사 착수. SKILL.md 파이프라인 반영(요구사항 확정 절차·G0 산출물 참조)은
   별도 배치에서 진행(현재 이 문서는 선행 정의만 — SKILL.md 본문 수정은 이번 배치 범위 밖).

## 축 도출 체인 (1:1 대응 강제)
```
의사결정 용도 → [BM 렌즈로 후보질문 생성] → 조사질문 → 축 → 에이전트 배정 → 3부 챕터
```
"의사결정 용도 → 조사질문" 화살표가 팀리드 감(感)으로 건너뛰어지는 것이 기획 부실의
주원인 — 사업성·수요·경쟁·벤치마크·산업구조 관련 조사면 `references/business-frameworks.md` 의
적용 맵으로 해당 렌즈(L1~L9)를 골라 후보 질문을 생성한 뒤 3~5개로 선별한다(렌즈는 질문
생성기일 뿐, 프레임워크 블록 이름을 축 이름으로 승격하지 않는다).
체인의 각 화살표는 1:1이다 — 조사질문 하나가 축 하나를 낳고, 축 하나가 에이전트 분할 단위
하나(또는 그 배수)가 되며, 그 축 이름이 그대로 3부의 챕터 소제목이 된다. 축 이름이 이 체인
바깥에서 새로 지어지면(예: 챕터만 있고 대응하는 조사질문이 없으면) 그 챕터는 채워지지 않는다.
축 프리셋(조사유형별 기본 축 목록)은 `references/report-format.md` 의 "조사유형별 목차 변형"
절이 유일한 진실원이다 — 이 문서는 그 프리셋을 어떻게 골라 쓰는지(도출 체인·품질 기준)만
규정하고, 축 이름 자체를 다시 나열하지 않는다.

## 축 품질 기준
- **MECE**: 축끼리 겹치지 않고(Mutually Exclusive), 합쳐서 조사질문 전체를 덮는다(Collectively
  Exhaustive). 겹치면 같은 수치가 두 축의 조사원에게 중복 수집돼 claim_key 충돌이 난다.
- **사실·수치로 종결 가능한 질문 형태**: 축은 서술형 주제가 아니라 답이 나오면 끝나는 질문이어야
  한다. "시장은 어떤가" ✗(끝없이 확장됨) → "2024년 글로벌 설치용량과 상위 5개국 비중은" ○
  (수치 확보로 종결 판단 가능).
- **축 3~5개**: 3개 미만이면 조사질문이 뭉뚱그려져 챕터가 과부하되고, 5개 초과면 에이전트
  분할이 과세분화돼 교차검증 비용만 늘어난다.
- **축별 "무너지는 결론" 한 줄**: 각 축에 "이 축이 답을 못 내면 어느 결론이 무너지는가"를
  한 줄 붙인다. 답을 못 내도 보고서 결론에 영향이 없는 축은 애초에 축이 아니라 참고정보다.
  서식은 `references/business-frameworks.md` L6(부하가정 — Fails if — 최저비용 검증)를
  쓴다 — G4 intent-diff 대조에서 이 Fails if 조건이 촉발됐는지 확인하고, 촉발분은 9부에 기재.

## 조사질문 항목 스키마 【v4-P】 (반례 선설계)
축별 핵심 조사질문은 서술형 한 줄이 아니라 아래 5열 스키마로 적는다 — 반례를 계획 시점에
설계해 두어야 조사원이 "지지 증거만 모으는 확증 수집"으로 흐르지 않는다.

| 열 | 내용 | 예시(수치형) |
|---|---|---|
| 질문 | 축 품질 기준을 만족하는 종결 가능 질문 | 2024년 글로벌 설치용량은 |
| 예상 claim | 예비탐색 기준 예상 답(모르면 "미상") | 약 N GW(기관 X 추정) |
| 필요한 증거 | 이 claim 을 confirmed 로 만들 증거 유형 | 1차출처 보고서 캡처 + 교차 1건 |
| 반례 쿼리 | claim 을 무너뜨릴 수 있는 검색 문장들 | 아래 기본 3종 + 축 특화 |
| 폐기 조건 | 어떤 결과가 나오면 이 claim 을 버리는가 | 타기관 추정치가 ±30% 밖 |

**수치형 claim 의 기본 반례 쿼리 3종**(생략 금지): ① 타기관 추정치 ② 타연도 수치
③ 타정의(모집단이 다른 같은 이름의 수치). 반례 쿼리는 조사원 브리프에 그대로 들어가고,
[Bx] 반박 게이트가 "계획 시점 반례 쿼리 전건 소진 + 더 강한 반박 없음"을 검사한다
(게이트 규정은 `references/verification-gates.md`).

## 의도 확정 (Intent Reconciliation) 【v4-P】
가정으로 때운 확정치 — 연도·지역·통화·포함 기준·언어 등 "물어보지 않고 그럴듯하게 채운
값" — 는 승인 전에 **영향이 큰 순으로 1개씩** 사용자에게 확인해 `audit/research-plan.md`
에 박제한다(한꺼번에 나열 승인받으면 개별 오류가 묻힌다 — 라운드당 1질문 규칙과 동일 원리).
**자동 플래그 대상 = research-plan 확정치 전체**: 조사 중 수집된 fact 가 확정된 기간·지역·
언어·시장 정의·out-of-scope 와 모순되면 그 fact 는 재검증 우선 타깃으로 플래그된다.

## typed 조향 【v4-P】 (계획 변경 프로토콜)
확정 이후의 계획 변경은 `audit/research-plan.md` 직접 편집 금지 — `audit/run-ledger.jsonl`
에 `kind: steering` 레코드를 append 한 뒤에만 계획 파일에 반영한다(레코드 스키마 정본은
`scripts/run_ledger.py` docstring):

```
steering {kind, op: add_item|split_item|reorder|revise_wording|supersede_item|annotate,
          evidence, rationale, at}
```

- 모든 조향은 `evidence`(무엇을 보고 바꾸는가)와 `rationale`(왜)을 요구한다 — 근거 없는
  조향 레코드는 무효.
- **불변식**: 사용자 확정 스코프(기간·지역·언어·out-of-scope)와 게이트 기준은 조향 불가 —
  바꾸려면 사용자 ask 로 재확정해야 한다.
- 원칙: **"산문은 상태를 변이하지 않는다"** — 대화·보고 중의 언급만으로는 계획이 바뀌지
  않으며, steering 레코드가 없는 계획 차이는 오염으로 간주해 되돌린다.

## 계획 합의 루프 (2레인 리뷰) 【v4-C】
팬아웃 직전(승인 3단의 feasibility 단), 확정 계획 초안을 2레인이 병렬 리뷰한다
(서브에이전트 2개 — 소규모 조사면 팀리드가 셀프 이중 렌즈로 두 관점을 순차 수행 가능.
리뷰어 브리프 원문은 `references/agent-briefs.md`).

| 레인 | verdict 원어 | 검사 대상 |
|---|---|---|
| 커버리지 리뷰 | `CLEAR / WATCH / BLOCK` | 범위 누락·씬 축(증거가 빈약할 축)·출처 전략 약점. "씬하면 확장 요구"가 유효한 지적이다 |
| 실행가능성 리뷰 | `OKAY / ITERATE / REJECT` | 대표 조사원 2~3명의 작업을 시뮬레이션 + **대상 도메인 1~2건 `fetch.py` 실측 프로브 결과 필수 슬롯**(도달 사다리 계층·차단 여부 — 추측 승인 금지) + Approval Boundary(승인 범위 vs 범위 밖) 명시 |

- **실측 실패는 REJECT 사유가 아니라 진단이다** — 차단·불달 도메인은 계획 조정(대체 출처·
  사다리 계층 변경) 입력과 `assets/domain-recipes.json` 갱신 입력으로 쓴다.
- **두 레인 클린(CLEAR + OKAY)일 때만 consent 단으로 진행**한다. 레인 verdict 원어는
  PLAN 게이트 checkpoint 의 `lane_verdicts` 에 보존 기록한다(환산 규정은
  `references/verification-gates.md`).
- 리뷰 지적은 전건 처분(accept/rebut) — 침묵 폐기 금지. accept 는 계획 수정(typed 조향
  경유), rebut 는 반박 사유 기록.
- **반복 상한 3회**: 3회 루프에도 두 레인 클린에 도달하지 못하면 `PLANNING-STUCK` — 최선안을
  보존하고 사용자 승인을 요청한다(자동 팬아웃 금지. 상한 없는 자가수렴 루프는 계획을 계속
  고치며 착수를 무기 연기하거나, 반대로 리뷰를 형식화한다).

## G0·PLAN 개입 지점 목록 【v4-A】 (asks — 스키마 정본은 verification-gates.md)
사용자 개입(ask) 프로토콜의 **스키마·규칙 정본은 `references/verification-gates.md` 의
asks 절이다**(활성 ask 1개·멱등·supersedes 계보·알림 의도 매핑 전부 그쪽 규정을 따른다).
이 문서는 G0·PLAN 단계에서 ask 가 발생하는 지점만 열거한다 — 각 지점은 run-ledger 에
`kind: ask / kind: answer` 로 기록된다.

| 지점 | 단계 | 내용 |
|---|---|---|
| 규모 판정 이견 | G0 | 직접 경로 안내에 사용자가 파이프라인 진행을 고집하는지 확인 |
| 13필드 초안 확인 | G0 | 초안 문서 1건 확인(=1라운드 1질문) |
| 인터뷰 라운드 | G0 | 라운드당 1질문(결정 라우팅된 것만) |
| 조기 착수 확인 | G0 | 케이던스 3라운드+ 의 "현재 명료도로 착수?" |
| restate 확인 | G0 | 목적 1문장 verbatim 확인 |
| 의도 확정 | G0/PLAN | 가정으로 때운 확정치 1개씩 확인 |
| consent | PLAN | 팬아웃 명시 승인(승인 3단의 마지막) |
| PLANNING-STUCK | PLAN | 합의 루프 상한 초과 시 최선안 승인 요청 |

## 승인 목차 예시 (기계 파싱 대상 — G3 목차 기계검사의 `--plan` 옵션이 이 서식을 정규식으로 읽는다)
부 번호·제목은 `# 부 N. 제목`, 3부 하위 축 챕터는 `## 축: 이름` 으로 고정 표기한다(정규식
`^# 부 (\d+)\.\s*(.+)$` / `^## 축:\s*(.+)$` 로 추출 가능해야 하므로 서식을 임의 변경하지 않는다).
예시(기술동향 유형, 축은 조사별로 승인된 값으로 교체):
```
# 부 0. 표지·메타
# 부 1. Executive Summary
# 부 2. 조사 개요
# 부 3. 테마별 본론
## 축: 기술요소
## 축: 플레이어
## 축: 시장
## 축: 정책
# 부 4. 시장 수치 종합
# 부 5. 연구기관 매핑
# 부 6. 검증 요약
# 부 7. 상충·모순
# 부 8. 상태 변화·주의
# 부 9. 한계와 반론
# 부 10. 한눈 요약표 + 조사팀 인사이트
# 부 11. 부록
```
11부 표준목차 골격(`report-format.md`) 자체는 조사유형과 무관하게 고정 — 승인 목차에서 바뀌는
것은 3부의 `## 축:` 목록뿐이다(유형별 축 프리셋은 `report-format.md` 참조).
